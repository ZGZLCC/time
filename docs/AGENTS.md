# 开发规范与要求

## 适用范围

- 本文件为整个项目的开发规范，由根目录 `AGENTS.md` 引用，覆盖前端、后端、测试和文档。
- 开始任务前阅读本文件、`docs/implementation-plan.md` 和 `docs/project-structure.md`，按当前需求和既定模块边界实现。
- 需求或关键设计变更时同步修订执行方案，保持方案与实际约定一致。
- 项目发生任何代码、配置、目录或文档改动时，检查并同步更新 `docs/project-structure.md`，确保目录清单和文件职责与实际代码一致；只记录已存在且可核对的内容，规划中的能力留在执行方案中。

## 前端设计规范

- 新建或修改前端页面、组件和样式前阅读并遵循 [`docs/DESIGN-webflow.md`](DESIGN-webflow.md)，将其作为项目的视觉设计依据。
- 亮色模式延用该规范的白色画布、近黑色正文与主按钮；暗色模式使用对应的深色画布、浅色文字及清晰边框。两种模式均延用标签强调色、字体层级、4 px 间距基准、按钮 4 px / 卡片 8 px 圆角和控件样式；强调色用于分类等内容表面，不用于主按钮。
- 专有字体不可用时使用设计文档列出的开放字体或系统回退。响应式断点和组件示例按桌面应用窗口适配，不照搬营销网站的导航、页面分区或示例内容。
- 保留项目现有的可访问性要求，包括足够的文字对比度、表单标签、键盘操作和清晰的焦点状态。

## README 要求

- 每次交付必须创建或同步更新根目录 `README.md`，使其准确反映当前交付结果；不按任务次数追加流水账。
- README 只描述当前已经做成、可以验证的结果，包括已交付文档、可用功能和实际具备的技术结构。
- 使用结果表述，例如“支持按周查看记录与分类时长”，避免“本次开发了周视图”“修改了某文件”。
- 禁止加入开发过程、尝试记录、进度流水账、待办列表、未来计划和“已做／未做”对照。
- 规划中的功能只写入执行方案；尚未验证的功能不得表述为已支持。
- README 保持简短；需要较长的说明时放入 `docs/` 并链接。

## 模块化与代码长度

- 按功能和职责组织代码；界面渲染、状态协调、IPC、业务规则、数据库访问各归其位。
- 单个人工维护的源码文件原则上不超过 250 行，Vue 文件包含模板、脚本和样式；接近上限即按职责拆分。
- 单个函数原则上不超过 50 行；较长分支或多项职责优先提取有明确名称的函数。
- 自动生成文件及依赖锁文件不计入长度限制；其他例外需写明不可合理拆分的原因。
- 不用压缩格式、堆叠单行或无意义拆文件规避长度要求；不建立只有单一实现且无实际需要的抽象层。
- `App.vue` 只负责页面组合；Tauri 命令只负责边界校验和调用；业务 SQL 集中放在数据库模块。
- 复用已有实现，优先标准库、平台能力及已有依赖；仅因当前功能需要才引入新依赖。

## 数据与业务约束

- 起止时间、标签、内容、状态转换及重叠规则以 Rust 后端校验为准，前端校验用于及时反馈。
- 所有入口复用同一套时间规则；修复问题前检查相关调用路径，避免只处理单个页面的症状。
- 时间存 UTC 毫秒，输入和展示遵循执行方案的北京时间口径；禁止混用秒、毫秒和无时区字符串。
- 周图、分类统计及总时长使用一致的区间裁剪结果；待补全记录不得悄然计入正式统计。
- 写入成功后再更新界面结果；失败时保留用户输入并显示可操作的提示，不吞掉错误。
- 数据库迁移必须保留已有数据，失败应回滚；禁止用删库重建处理升级或读写异常。
- 参数化 SQL；内容作为纯文本渲染；Tauri 权限只开放当前功能实际需要的能力。
- 不提交真实时间记录、数据库、个人数据或本机绝对路径到源码和示例数据中。

## 界面与验证

- 标签颜色及名称统一维护；颜色之外同时提供文字，表单有标签，按钮和详情支持键盘操作。
- 非平凡业务逻辑至少保留一项可运行检查；覆盖真实边界和曾出现的问题，避免只复述实现的测试。
- 按改动范围执行类型检查、相关业务测试和必要的构建；桌面交付必须验证安装启动、重启持久化和升级数据保留。
- 文档任务检查文件位置、链接、需求覆盖与前后一致性；不为纯文档或简单样式改动搭建测试框架。
- 交付前核对 README 的每项结果都有对应文档、实现或验证依据。
- 项目改动交付前检查 `docs/project-structure.md` 是否需要同步；新增、删除、重命名文件或职责/行为变化时必须更新。

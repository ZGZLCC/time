# 时间记录应用执行方案

## 1. 技术选型

| 部分 | 选型 | 职责 |
| --- | --- | --- |
| 桌面容器 | Tauri 2，面向 Windows 10/11 x64 与 macOS | 窗口、本机通信、安装包；复用系统 WebView |
| 前端 | Vue 3 + TypeScript + Vite | 记录表单、打卡入口、周视图和统计展示 |
| 后端 | Rust + Tauri Commands | 数据校验、打卡状态、时间计算、数据库读写、云端快照合并 |
| 存储 | SQLite + rusqlite（bundled） | 默认存于用户应用数据目录，支持一致性备份与从备份恢复 |
| 界面 | 原生 CSS、CSS Grid、自绘日期与时间控件 | 七天时间网格、标签颜色、响应式布局、不依赖系统默认日期时间控件 |
| 构建 | npm + Cargo，提交各自锁文件 | 固定依赖、类型检查、测试和桌面打包 |

前端使用 Vue 组合式函数管理状态；按实际功能增加依赖。应用资源随安装包提供，业务功能离线运行。

技术依据：[Tauri 架构](https://v2.tauri.app/concept/architecture/)、[Tauri Commands](https://v2.tauri.app/develop/calling-rust/)、[Vue TypeScript](https://vuejs.org/guide/typescript/overview.html)、[rusqlite](https://docs.rs/rusqlite/latest/rusqlite/)。

## 2. 架构与模块

数据流：Vue 组件 → 组合式函数 → 类型化 IPC 封装 → Rust 命令 → 业务规则 → SQLite；云同步在前端发起 HTTP 请求，合并与写回仍由 Rust 决定。

Rust 运行于桌面主进程，前后端通过 Tauri `invoke` 通信。后端作为记录状态、区间校验和统计结果的唯一业务来源；前端负责输入、格式化及布局。

当前仓库的实际结构与职责见 [项目结构与代码功能](project-structure.md)，改动时按规范同步维护该文档。按职责划分的模块边界如下：


## 3. 数据与时间规则

记录表 `time_entries`：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | INTEGER | 主键，由数据库生成 |
| `start_ms` | INTEGER / NULL | UTC Unix 毫秒时间戳；草稿可为空 |
| `end_ms` | INTEGER / NULL | UTC Unix 毫秒时间戳；草稿可为空 |
| `start_date`、`end_date` | TEXT / NULL | 保存仅选择日期、未填写具体时间的草稿输入 |
| `content` | TEXT | 事情内容；去除首尾空白后不超过 500 字，草稿和已完成记录都允许为空 |
| `tag` | TEXT / NULL | `work`、`leisure`、`sleep`、`other`；已完成时必填 |
| `state` | TEXT | `running`、`draft`、`completed` |
| `public_id` | TEXT | 跨端稳定标识（UUID），首次写入时生成，两端靠它对应同一条记录 |
| `updated_at` | INTEGER | 修改时间（UTC 毫秒），同步按它做「后写胜出」 |
| `deleted_at` | INTEGER | 删除墓碑（0 表示未删除），参与同步比较，删除才能传到其他设备 |

- 首版输入、周边界和展示统一采用北京时间 `Asia/Shanghai`（UTC+08:00）；数据库保存 UTC，系统时区变化不改变历史记录的展示口径。
- 一周为周一 00:00 至下周一 00:00；所有区间按左闭右开 `[start, end)` 处理，首尾相接允许保存。
- 两个时间均已填写时满足 `end_ms > start_ms`；手动录入以分钟为精度，打卡仅保留实际开始时间戳。
- 已完成记录之间禁止时间重叠；编辑时排除自身。冲突检测和写入位于同一事务中，冲突时显示对应记录并保留表单输入。
- 待补全记录可以暂时与其他记录交叉；转为已完成时执行统一的完整性和重叠校验。
- 数据库通过 `CHECK` 约束标签、状态及已完成记录的必填字段，并为时间范围查询建立索引；迁移保留旧记录并将旧 `running` 状态转为待补全。
- 数据库默认保存于 Tauri 用户应用数据目录 `time-v3.sqlite3`（1.3.0 起）。首次启动 1.3.0 时把旧的 `time.sqlite3` 原样复制成新库再迁移，旧文件一个字节都不改、留在原目录当备份。用户也可将其迁移至所选文件夹；应用数据目录保存当前数据库路径，重启时恢复；配置位置的文件不可用时提示错误，不新建空库。写入即时提交。版本迁移前按版本号留下 `.v{N}.bak` 快照，失败回滚并保留原数据库。

## 4. 记录与打卡

记录页桌面布局为左侧白底快速记录和待补全卡片、右侧默认展开的手动记录卡片；左侧两张卡片的总高度与右侧相同。待补全一次显示最多三条，多余记录在卡片内滚动；缺失日期或时间分别显示 `xxxx-xx-xx`、`xx:xx`。下方整行展示记录历史，记录行以单行起止时间为标题、右侧显示标签、正文显示事情内容。历史默认显示全部已完成记录，最多完整显示五条、其余在卡片内滚动。历史右上角提供与周视图一致的“跳转日期”控件，选择日期后只显示该日记录（跨午夜记录计入其覆盖的每一天），选择日期后出现“全部”按钮恢复显示全部记录。页面与卡片内隐藏滚动条，保留滚轮、触控板和键盘滚动。

起止日期与时间使用项目自绘控件：日期是七列日历（周一起始、固定 6 行以免切月跳动、今天带边框、选中加深加粗），时间是小时与分钟两列的滚动选择器（两列都能无限循环，中间高亮带表示当前选中，打开时默认落在当前时刻），不使用浏览器或系统的默认日期时间控件。

1. 手动记录：起止日期和具体时间分开输入；选定一侧日期时，另一侧默认同一天且具体时间保持空白。缺时间、内容或标签时可保存为待补全草稿；有起止时间和标签即保存为已完成记录，内容允许为空。
2. 快速打卡：每次点击由后端获取当前时间，立即新增一条仅含开始时间的待补全草稿，不自动填写结束时间。
3. 补全记录：补充或修正起止时间、内容和标签；全部完整后保存为 `completed`。
4. 待补全列表只显示起止时间，缺失位置以 `x` 占位；支持“补全”或居中确认删除，三条以上在卡片内滚动，应用重启后恢复。
5. 写操作期间禁用重复提交；每次打卡均新增独立开始时间。提交成功后刷新记录、周视图和统计，并广播一次数据变化，让被缓存的页面重新读取。

## 5. 周视图与统计

- 查看页采用随窗口宽度适配的七列日期、纵向 00:00～24:00 网格；事件块的位置与高度按实际起止分钟计算，支持不足一小时的记录。
- 标签固定映射：工作蓝色 `#2563EB`、娱乐橙色 `#C2410C`、睡觉紫色 `#7C3AED`、其他灰色 `#475569`；使用统一颜色变量，图例同时显示中文标签。
- 事件块显示事情内容；空间不足时截断，点击或键盘激活会滚动并聚焦到时间表上方的记录详情。详情以完整起止时间为标题、事情内容为正文，并可进入编辑；短记录仍保留可操作的最小高度。
- 跨午夜记录按天生成显示片段，各片段关联同一原始记录；数据库保留一条完整记录，编辑任一片段均修改原记录。
- 提供上一周、下一周、回到本周及日期选择；选择任意日期即定位其所在周，标题显示完整起止日期，支持跨月、跨年浏览。
- 周图和正式统计仅包含已完成记录；查看页提供待补全数量及入口，未记录时段保持留白。
- 周查询使用区间相交条件 `start_ms < week_end && end_ms > week_start`，覆盖开始于前一周、结束于本周的记录。
- 每条记录本周计入时长为 `max(0, min(end_ms, week_end) - max(start_ms, week_start))`；按标签汇总后相加得到已记录总时长。
- 周视图最上方为所选日期已记录卡片，显示该日四个标签各自的时长，样式与本周卡片一致且不显示合计；下方依次为本周卡片和累计卡片，累计卡片显示全部已完成记录按四个标签分别累计的时长，均不显示合计时长或记录条数。统计按实际毫秒累加，展示层舍去不足一分钟部分。切周和跳转日期时保留当前画面，查询成功后直接切换到目标周，不显示中间加载内容。
- 该卡片跟随顶部当前选中的日期，不固定显示今天：标题为完整日期标题（如 `2026年10月4日已记录`）并与选中日期一致，选中今天时追加“（今天）”。切换周、回到本周和跳转日期都会重新读取该日统计；本日统计与周统计共用同一套裁剪规则，只是区间取当天 00:00～24:00；跨午夜记录按落入当天的部分计一次，不足一分钟显示为 0。
- 时间表下方提供 PNG 周记录图片导出：图片包含所选周的七天时间表和工作、休闲、睡眠、其他四项本周时长，统计区与表格之间留出清晰间距；输入文件夹地址或用系统对话框选取，默认地址由系统 Downloads 目录取得；地址为空时禁用导出，文件名包含周起止日期，重名时改用带序号的文件名并保留已有图片。
- 周图片段和统计共用后端裁剪规则；例如周日 23:00→周一 01:00，两周分别计入一小时。北京时间口径下每周已记录总时长不得超过 168 小时。

## 5.1 设置与主题

- 设置页依次展示云端同步、备份与恢复、本地数据、修改主题四张整行卡片；备份与恢复沿用周图片导出的地址输入、系统文件夹选择和操作按钮布局。
- 导出备份以 SQLite 在线备份生成一致的 `.sqlite3` 文件，默认地址为系统下载文件夹，重名时改用带序号的文件名，不覆盖旧备份。
- 从文件恢复先用项目自己的确认框说明后果，再用备份内容整体替换当前记录；恢复本身不额外留快照，只有 schema 升级时 migrate 才会在改动前留下 `.v{N}.bak`。只接受当前 schema 或更新的备份，更早的备份明确报错，而不是做有损恢复。
- 清空记录是软删除并保留删除墓碑，避免其他设备同步时把记录推回来。
- 本地数据卡片显示已完成与待补全条数以及上次导出备份时间。
- 修改数据库位置的能力保留在后端命令中；当前界面不再提供该入口。
- 主题为跟随系统、亮色、暗色三个等宽按钮；默认跟随系统，选择保存在本机，重启后恢复。暗色主题覆盖画布、卡片、表单、网格、文字、焦点和标签；导出的 PNG 保持固定浅色配色以便阅读。

## 5.2 云端同步

- 桌面版与网页版共用同一个 Cloudflare Worker 和同一份记录契约，用管理员创建的同步码区分数据：一个同步码对应一份独立数据，未填写同步码时不发出任何请求。
- 跨端身份用 `public_id`（UUID）；合并按 `updated_at` 后写胜出，删除写成 `deleted_at` 墓碑参与同一比较，因此删除能传到其他设备，也不会被别的设备上的旧副本复活。
- 墓碑的用途是让离线很久的设备知道自己删过什么，所以不能立刻删；保留期为 180 天，两端必须用同一个值，超过保留期后由本地与云端分别真正删除。
- 「立即同步」逐条双向合并；「上传本地记录」用本机内容整份覆盖云端（上传带 `replace=1`，云端不做逐条合并）；「从云端恢复」用云端内容整份覆盖本机。两个覆盖方向都会先弹居中确认框说明后果，被覆盖掉的记录靠墓碑传到其他设备。
- 同步走系统代理；连不上、同步码不存在或已停用、返回内容无法解析都给出可操作的中文提示，本地记录不受影响。

## 6. 本地命令接口

| 命令 | 输入 | 输出或行为 |
| --- | --- | --- |
| `save_entry` | 可选 ID、起止时间、日期、内容、标签 | 新建或补全、更新已完成记录，返回保存结果 |
| `delete_entry` | ID | 软删除指定记录，保留墓碑 |
| `start_punch` | 无 | 新增仅含开始时间的待补全记录 |
| `list_pending` | 无 | 返回全部待补全草稿及兼容旧状态记录 |
| `list_entries` | 无 | 返回全部未删除的已完成与草稿记录 |
| `get_week` | 所选日期 `YYYY-MM-DD` | 返回周边界、原记录、每日显示片段、四类时长及总时长 |
| `get_day_totals` | 目标日期 `YYYY-MM-DD` | 返回该日 `[00:00, 24:00)` 内四类标签的裁剪时长 |
| `get_all_totals` | 无 | 返回全部已完成记录按四类标签累计的时长 |
| `default_export_directory` | 无 | 返回系统 Downloads 文件夹路径 |
| `save_week_image` | 文件夹、周起止日期、PNG 字节 | 校验并保存图片，返回最终文件路径 |
| `database_directory` | 无 | 返回当前数据库所在文件夹 |
| `export_database` | 文件夹 | 导出当前数据库的一致性备份，返回新文件路径 |
| `move_database` | 文件夹 | 复制并校验数据库、切换位置，返回新文件夹路径 |
| `clear_entries` | 无 | 软删除全部记录，返回受影响条数 |
| `purge_tombstones` | 当前时间 | 真正删除超过保留期的墓碑，返回删除条数 |
| `pick_backup_file` | 无 | 弹出选择备份文件的对话框；取消时返回空 |
| `restore_database` | 备份文件路径 | 校验 schema 版本后整体替换当前记录，返回恢复条数 |
| `cloud_snapshot` | 无 | 返回本地全部记录的云端格式快照（含墓碑） |
| `merge_cloud` | 云端快照 | 按 `public_id` 逐条合并（后写胜出），返回写回条数与待推送记录 |
| `mirror_cloud` | 云端快照 | 用云端快照整体覆盖本地，返回写入条数 |

命令入口校验参数，统一返回可识别的错误码和中文提示；前端不直接操作 SQLite。内容按纯文本显示，数据库使用参数化查询。

安装升级约定：Windows NSIS 使用 `both` 模式，并在安装前检查 HKLM 与 HKCU 的旧安装登记目录；只有一处旧安装时自动沿用该范围和目录，两处同时存在时沿用安装器所选范围，在原目录覆盖程序文件，不修改独立的应用数据目录。为让升级不需要额外选择，仓库内保存了基于 Tauri CLI 2.11.x 的 NSIS 模板快照 `src-tauri/windows/installer.nsi`，其中 `PageReinstall` 在检测到已有安装时直接 `Abort`，因此安装器跳过“维护选项”（Already Installed）页，直接进入安装位置页（默认已填原目录）并原位置覆盖升级；没有既有安装时保持默认的分范围与选择位置流程。模板随 Tauri 版本升级时需重新对照更新。此模式启动时需要管理员权限。安装包不做代码签名，Windows SmartScreen 对新版本首次运行会给出“无法识别的应用”提示，选择“更多信息 → 仍要运行”即可，或在获得代码签名证书后按 Tauri 的 `bundle.windows.certificateThumbprint` 配置签名。macOS 在原有 `.app` / `.dmg` 之外提供 Apple Installer 组件包构建脚本：在 Mac 上构建应用后执行 `sh scripts/build-macos-package.sh`，生成 `.pkg`。组件包以同一 bundle ID 识别已有应用并在原位置升级；构建目录中的 `.app` 副本会移成非应用目录，避免本机测试时被误识别。macOS 的原位置升级需在 Mac 上验证，且多个相同 bundle ID 副本时须核对实际覆盖位置。[Apple 组件包说明](https://developer.apple.com/library/archive/releasenotes/General/SubmittingToMacAppStore/)。

开发及打包前置条件按 [Tauri Windows 环境要求](https://v2.tauri.app/start/prerequisites/) 检查；安装包检测 WebView2，缺失时按 [官方安装方案](https://v2.tauri.app/distribute/windows-installer/) 引导安装。
macOS 构建使用 Node.js、Rust 与 Xcode Command Line Tools；在没有 Mac 开发环境的前提下，交付改由 `.github/workflows/macos-build.yml` 在 GitHub Actions 的 `macos-15`（Apple Silicon）上完成：`npm ci` 后执行 `npm run tauri -- build --target aarch64-apple-darwin --bundles app`，用 `ditto` 把 `Time.app` 压成 zip 作为主产物，`.dmg`（以及基于 `productbuild` 的 `.pkg`）作为可选路线单独尝试，失败不影响交付。应用声明最低系统版本 macOS 11.0，测试构建使用临时签名；未签名产物首次打开需在「系统设置 → 隐私与安全性」里允许一次。正式分发若要做到双击即开，需配置 Apple Developer ID 证书并公证，workflow 已预留按 Secrets 启用签名的位置。

网页版是同一套功能的浏览器实现，随相册站点仓库维护，与桌面版共用同步服务与记录契约，其方案见该仓库的 `web/docs/implementation-plan.md`。每个阶段同步更新根目录 `README.md`，只陈述当时已交付且可验证的结果。
